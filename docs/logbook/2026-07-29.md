### PR #78 — coverage evidence integrity (rounds 13 → 16)

Reached **sixteen rounds**. Heads today: `a12e389` (r14), `24a905f` (r15), `1415dd3` (r16, in review at time of

**The headline fact: the GitHub connector found a real defect on six consecutive heads that were both CI-green

That is the single most important datum of the day, and it is why the merge gate reads the connector in a call

Round-by-round, what was actually closed:

- **r15** — the fix in r14 tripped our own semgrep rule `agenttalk-no-raw-agent-name-in-filename`:
  `candidate = f"state/{cursor.group(1)}.cursor"` interpolated a captured name into a path without the canonical
  validator. **This was the 7th grammar branch — the one the lead's brief had omitted when it summarised the
  exclusion class as "six families".** The reviewer had reported that 7th branch as "not a gap, just not in your
  paraphrase"; it is the one that broke the build. Routing it through `validate_agent_name()` then exposed a real
  exemption: `state/operator.cursor` had been treated as scanner state, because the hand-rolled regex lacked the
  reserved-principal rejection the canonical validator has.
- **r16** — the connector found `TOTAL 10 10 99%` parsing as 99% coverage: ten statements, ten missed. **This is
  r13's finding on the other grammar** — "captures two numbers, validates one" was closed for the native
  pytest-cov sentence and never carried to the coverage.py row. Sent back as a class rather than a row, which
  found the branch mirror affected too (`TOTAL 10 10 20 0 99%`) and a third contradiction the connector never
  reported (`TOTAL 2 1 2 1 25%`: `Branch=2` permits one branch source and `BrPart=1` proves it executed).

**What was rejected, and why:**

- **Deferring the r16 finding to a follow-up task.** Tempting at sixteen rounds. Rejected because it is a
  false-GREEN in the exact mechanism the PR exists to make trustworthy — stdout is now the sole coverage

- **Fixing the config-lock-churn residual in-round.** The reviewer recommended *disclose, don't fix*: the failure

- **Raising the CI leg cap before merge.** Escalated to a release blocker on a figure the lead supplied and got

**Cost:** four rounds in one day, three CI cycles, one CI cycle wasted on a red that was a pre-existing flake.

### PR #92 — held for #102

The design answer accepted all five findings with no refutation and correctly designed rather than patched. The
primitive is `python -I -m agenttalk` at every B2 invocation: `-I` exists on 3.10, ignores `PYTHON*` inputs and
the CWD/script-directory prefix for that interpreter, **but does not delete those variables from `os.environ`** —
so an isolated wrapper can still hand the untouched code-under-test environment to the model and its
subprocesses. That is precisely what the current process-wide export cannot do, and why it contaminates the
thing it is meant to protect.

Two alternatives were rejected with reasons worth keeping: per-invocation clear/force remains a *denylist* and
does not close the 3.10 CWD-shadow channel; and entrypoint self-isolation is **too late**, because
`python -m agenttalk` resolves and imports `__main__` before package code could repair or re-exec — a shadow
checkout has already executed. On the second P1 the answer refused the easy exit: documentation is not
sufficient when the config accepts a 3.10 pin, the mechanism silently fails open there, and `--version` can
false-green from the shadow checkout. So #92 waits for #102's complete invocation-class change.

## Incidents

### 1. All six wrapped agents died inside a nine-second window (12:27:40Z) — cause undetermined

The supervisor went from normal polling to `poll_summary: healthy_idle=0, states={WRAPPER_MISSING=6}` in one
tick. **Six candidate causes were eliminated with evidence**, which is the useful part of an unresolved
incident:

| ruled out | evidence |
|---|---|
| supervisor teardown | no kill/teardown action anywhere in its event log |
| deadman | config is a mail-age alarm; no deadman process, no deadman log |
| a scheduled-job cancellation | in-memory schedule entry only, and ~10 min off the event |
| process crash | nothing in Application/System/Defender logs at 14:27:40 local |
| bus `end`/`wake` signal | no such message in the last 400; none written 12:18Z–12:32Z |
| per-wrapper lifetime | wrappers started at four different times and died together |

Remaining unfalsified and untestable after the fact: a console/session control event reaching the wrappers'
process group, which would terminate them cleanly, leave no OS fault record, spread over a few seconds of
polling jitter and spare a differently-hosted parent. It matches every observed property — which is exactly why
it must not be believed without evidence.

**The recovery asymmetry is the expensive part.** The two Claude agents self-healed in three minutes; the four
codex agents faced **~38 minutes** because their staleness threshold is 2400s against 180s. That is #87's cost,
measured on a real event rather than argued. Filed **#110**: a vanished wrapper leaves only a stale heartbeat, so
"killed" and "exited cleanly" are indistinguishable — record exit provenance, record launch topology, and treat
N-agents-absent-in-one-poll as a single correlated incident.

### 2. The supervisor could not start after the operator's reboot — three tool bindings, not one

`supervisor.ps1` refused to claim its instance: generated artifacts "stale or mixed". Regenerating them did not
help, because the writer and the validator were **different installs**:

```
python  -> C:\Program Files\PyManager\python.exe -> site-packages agenttalk 0.79.0   (wrote the artifacts)
PATH    -> ...\Programs\Python\Python314\Scripts\agenttalk.exe -> EDITABLE, 0.79.1   (validated them)
supervisor.ps1 pins $AgenttalkPython -> the 0.79.0 tree
```

Resolved by installing the checkout non-editably into the environment the supervisor actually pins, then
regenerating. **Residual, and it is sharp:** the PATH binding is still editable, so it tracks whatever branch
the checkout is on — switching the main checkout's branch will re-break supervisor validation. Work in a
worktree. This is #93's two-bindings thesis and #103's doctor-probes-a-different-executable, both manifesting
as an outage rather than a theory.

### 3. One message retried for fourteen hours — and the two obvious remedies did nothing

An agent re-attempted a single message **12 times**, each attempt killed by the ~1800s turn watchdog, every
failure classified `ambiguous_or_unknown`, so `poison_eligible_failures` stayed 0 and `escalated` stayed false.
`rescind` closes only the *thread*; the wrapper retries the *message*. A cursor advance moved the inbox pointer
and attempts still climbed 10 → 12. **The retry is driven by the per-message dead-letter attempt record, and a
reboot does not clear it** — the loop would have resumed at attempt 13 after a restart. Only killing the wrapper
and clearing that record stopped it. Filed **#109**: `dead-letter {list,show,requeue,resolve,purge}` all act on
messages already in the sink, which an all-ambiguous history can never reach, so the escape hatches are
unreachable precisely for the messages that need them.

### 4. A recurring pwsh hang cost roughly thirteen hours of agent time

Two different agents, two unrelated tasks, byte-identical signature: a `pwsh.exe` descendant hangs ~1750–1790s
and the turn watchdog kills the entire turn. Filed **#112**. The blocking problem is diagnosability: the record
names only `pwsh.exe pid=N age=Ns` — never the **command line**. Identifying the command required reading a
35 MB rollout in which the offending call was tens of minutes back, i.e. not recoverable in practice. Capturing
the command line before the kill is the smallest change that makes this fixable.

A hypothesis was explicitly **disconfirmed**: the two agents that hung were the *small, young* sessions
(30 MB / 35 MB, 4 days) while two sessions at 64–67 MB and 23 days ran clean all day. Session bloat does not
explain the hang, and that non-correlation is recorded so it does not become received wisdom.

## Decision: session lifetime is bound to the work item (#16)

Fresh session when a work item starts, warm across its rounds, reset when it closes, **never mid-round**.

Rejected: *never resetting* (measured cost — two agents at 171 and 230 turns, 64–67 MB replayed per turn,
against a documented crash at ~73 MB / 187 turns); and *a pool of per-domain "experts"* (the capacity argument
survives, the expertise argument does not — see #87 above, plus the fact that a rollout is a verbatim log of
superseded scratch work, that stale context is indistinguishable from knowledge until it is wrong, and that
context is the one store you cannot retract from, where `knowledge curate` can).

A counter-argument was recorded rather than omitted, because it nearly changed the decision: a reviewer's
round-16 value came partly from remembering a round-12 concern. But that concern lived in its review-result
`residual_risk` field on the bus, which is how it was re-raised — **unresolved concerns belong on the bus, not in
a reviewer's head** — and the inverse risk is real, since a reviewer that remembers approving round 14 is
anchored when reviewing round 15.

Corollary: a size/turn/age bound must **alarm, not act**. An automatic reset can fire mid-round and destroy
in-flight work; today it would have discarded nineteen minutes.

## Corrections — the lead was wrong four times

Recorded because a logbook that only lists successes teaches nothing.

1. **"The leg is at 92% of its cap."** Conflated two timeouts: 1800s is *semgrep's*, pytest's is **2700s**. The
   true figure was 61% with 17.5 minutes of margin. The retired 1800s number came from stale notes (the cap was

   blocker on a false premise. The reviewer re-derived the numbers from the files itself before accepting the
   correction. **Rule adopted: never say "the cap" without naming which of the four timeouts.**
2. **"The rescind stopped the retry loop."** It did not, and neither did the cursor advance — see incident 3.
   Reported as a fix before verifying that attempts stopped climbing.
3. **Twice claimed a process was running** from a `CommandLine -match` filter that matched *the shell executing
   the query*. Asserted a live supervisor and a live deadman when neither existed. Fix: enumerate processes and
   exclude `$PID`.
4. **Blamed our own tooling for a transient transcript write failure.** Disproved by reading the code:
   `capacity.py` reads a small sidecar, not the transcript. The lock probe used to "confirm" it was also invalid,
   since requesting exclusive access always fails while the legitimate writer holds the file.

The common shape across 1–4: **checking the state being asserted rather than the state that would falsify it.**
