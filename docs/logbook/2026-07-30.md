## What this day was about

Yesterday ended with a P0 design (supervisor recovery authority) under review and a fleet that had died
twice. Today the design work continued, but the day was dominated by something else: **the wrapped runtime
kept eating its own throughput**, and we finally measured it precisely enough to name it a constant rather
than a series of incidents.

The headline number: **nine wrapper wedges**, at turn-elapsed **1804.8s, 1811.7s, 1788s, 1766s, 1791s,
1765s, 1811s, 1808s, 1793s** — every one within ~35 seconds of the per-turn watchdog's 1800s deadline. Nine
for nine.

## The mechanism, and how it was narrowed

Established from `.agenttalk/state/<agent>.wrapper-runtime.json` arithmetic: subtract `cli_launcher_start`
from `last_progress_at`. If it lands near 1800s, the per-turn watchdog fired, killed the tool tree, and the
wrapper then **failed to fail its own turn** — it froze at `phase="active"`, `last_outcome=null`, heartbeat
and `progress_sequence` stopped at the same instant. Longest observed freeze: 249 minutes.

Three successive narrowings, each one correcting the previous:

1. First framing (task #110): "a wrapper that vanishes leaves no exit provenance." True but shallow.
2. Root cause found (task #112): the watchdog's *own* kill wedges the wrapper it was protecting. Verified by
   process-tree enumeration — the killed wrapper had **no codex descendant, only `conhost.exe`**.
3. The lead then proposed a cheap fix: "the shutdown path already writes the terminal record, so route the
   watchdog kill through it." **codex-agenttalk-developer-7 refuted this with the code** (PR #101): the unwind
   machinery *did* publish `terminal/failed`, but the owner thread never reached it, because `_ProcStream`
   waited synchronously on stdout EOF and an inherited writer — the very `conhost.exe` the lead had
   observed — keeps that pipe open after the child tree dies. The good terminal record the lead saw came from
   *external* shutdown later. Calling the shutdown writer from the watchdog thread would not have released
   the blocked turn loop.

That is the day's best piece of work: a worker taking the lead's own evidence and showing the lead had drawn
the wrong conclusion from it.

## Why the wedges keep happening — and the standing rule that came out of it

Task #121: the per-turn watchdog fires when a turn exceeds `turn_elapsed_seconds`=1800 **and** a live
non-codex tool descendant has been alive ≥ `tool_descendant_alive_seconds`=600. `dev-gate.json:64-73` caps
the source pytest leg at **2700s**. So running the project's own gate inside a wrapped turn satisfies both
watchdog conditions **by doing the job correctly**. `supervisor.py:5591` documents this as a known
limitation; we were the case that comment warns about, and nobody had raised the values.

The discriminator was never agent identity or luck: agents writing code and design crossed the same boundary
a dozen times without dying; the agent running the gate died five times.

Operator decision: **do not raise the thresholds** (that disarms the protection and stretches absent-wrapper
recovery from 40 to ~95 minutes). Instead, a standing directive — **agents own the tests, the build server
owns the build.** Targeted tests for the diff in-turn; never the full gate, suite, wheel legs or security
stack; push and let authoritative CI gate.

`claude-agenttalk-reviewer-fable` then found a defect in the lead's own wording: *"wait for and read the CI
result"* cannot mean holding a turn open, because CI outlives the turn and would trip the exact watchdog the
rule exists to avoid. Corrected mechanism: push, **end the turn cleanly**, report per-lane on the next wake.
It also noted that targeted-only testing sharpens the unpinned-interpreter trap — a worktree's targeted
pytest silently imports the main checkout unless `PYTHONPATH` is pinned — so `CWD=<worktree>` **and**
`PYTHONPATH=<worktree>/src`, both, every time.

## The livelock (task #122)

One agent lost **nine hours** to a failure the lead could not see. Because a wrapped agent processes one
inbound message per turn, and because a wedged turn never completes, it retried the *same* message five
times. Its queue at discovery:

```
q-7b8c23bc5b33  "#117 GO"                                   9h unread  <- the cause
q-4ead2072d85b  "RESUME #114 ..."                           2h unread
q-d37827754601  "STANDING RULE: never run the gate in-turn"  1h unread  <- the fix
```

**The instruction that would have prevented the wedge was queued behind the instruction causing it.** Nothing
caught it: the dead-letter attempt record was literally `{"messages": {}}` because the turn never *failed*, it
froze. The supervisor reported `HEALTHY_WORKING`. From the lead's side it looked like busy → recovered → busy,
five times.

Fixed for the instance by `agenttalk rescind` on the head message. Recorded as a structural gap: rescind is a
queue remedy, not a recovery mechanism.

## Recovery authority: what works and what does not

Measured, not argued:

- `request-restart` **works** when the wrapper is genuinely absent — killed, or never launched. Measured
  ~22–90 seconds from request to healthy, versus up to 40 minutes waiting out heartbeat staleness.
- `request-restart` **does not work** on a live wedge. Both outcomes in the same second:
  `16:27:56 MANUAL_RESTART relaunch` and `16:27:56 LAUNCH_BLOCKED same_agent_wrapper_survived`. The barrier is
  *correct* — a second wrapper would race the mailbox — but nothing owns terminating the incumbent (task #78,
  retitled today to say exactly this).
- The failed-recovery cycle **backs off exponentially** (33s/65s/129s/244s/487s), so a permanently wedged
  agent becomes progressively *less* likely to be retried and its operator-visible signal gets *rarer*. A
  bounded cycle is therefore not sufficient; it needs a cap that escalates.
- Self-recovery happens but is **not** a designed timeout: measured 57, 64, 73 and ~73 minutes, and once not
  at all within 249 minutes. Four wedges, four different outcomes — which is the strongest argument for making
  the failure deterministic.

## Fleet doubled

Operator authorised more developers. Added 1 Claude + 2 Codex, taking the fleet to **9 managed agents, 6
developers**. Config edited with Python rather than PowerShell, because `ConvertTo-Json -Depth` collapses
nested objects (proved on #115); atomic replace, every pre-existing entry asserted byte-identical, backup
retained.

**Task #123 found in the process:** a newly-added agent **never auto-launches.** All three sat at
`CLI_CHILD_UNKNOWN / action=none` on every poll — the one state that by design carries no launch authority. A
never-launched agent has no child, so routing it through the child-ambiguity path parks it permanently.
`request-restart` fixed it in ~22 seconds. The failure is silent: `status` shows `health=unknown`, which reads
like "starting" rather than "will never start."

All three new agents shipped a PR within ~80 minutes of their first dispatch, and none collided — the
file-region exclusions in their briefs held.

## The automated reviewer nobody was reading

Late in the day: `chatgpt-codex-connector` has been posting inline reviews on every ready PR, and the lead had
not looked at one all day — despite a banked lesson from PR #78 saying the merge gate must read the connector
and not just green CI.

Eight inline findings across two PRs. The connector flagged the PR #100 console-render defect as **P1 at
15:29**, thirty-three minutes before the bus reviewer reached the same conclusion at 16:02. Four further P2s
were things no bus reviewer caught at all, including one that corrects a misreading in this very logbook's
neighbourhood: **`CLI_CHILD_MISSING` is the supervisor's deliberate first-poll provisional state**, awaiting a
second confirming poll before `CLI_CHILD_DEAD`. The lead had read the alternating MISSING↔UNKNOWN as
bistability; it is a designed anti-false-positive confirmation policy, and treating it as terminal bypasses
that policy.
