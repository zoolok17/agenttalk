# 2026-08-02 — a one-second glitch, three wrong diagnoses, and the shape of a universal claim

## PR 98 merged after 30 rounds (`ee6ef0f`), and the review paid for itself twice

`#117` shipped: bounded per-agent stdout/stderr capture, a shared `console_main` so an uncaught
exception is bounded on every entry point, Preflight fidelity for declared interpreter prefixes, and
wrap-dispatch validation that asks agenttalk's own parser instead of hand-modelling a third grammar.

Thirty rounds looks like thrash and was not. **Green CI was wrong on that PR essentially every time it
was green.** The value came from two structural closures, and both *deleted* code:

- exactly one hand-built `cfg_agent` in the tree, made to store the launch dict **wholesale**, so every
  later lifecycle function preserves a future field for free — ending a three-round field-loss class;
- `_open_tail` may open a suffix with `wb` **only if this instance has itself already opened that exact
  index before, this run**. One attribute at the single place segments get opened. That made five
  separate byte-loss mechanisms impossible at once (unbounded second tee, size-assumption trade-off,
  mtime ambiguity, missing-cursor fallback, cursor-persistence-failure cascade) and let the one-shot
  resume-append flag be deleted.

Truncation stopped being a function of index *selection* and became a function of visit history. That
is why stale, missing and correct cursors all became safe under one rule instead of three fixes.

**Standing conclusion: closing the class kept being the cheaper option, not the expensive one.** I
should stop treating it as the ambitious choice.

## The orphaned fleet: a one-second glitch that disabled auto-recovery for hours

The operator saw `0/9 agents healthy` and nine repeating `PROCESS_TREE_INVALID … HOLDING automatic
teardown` warnings. The agents were fine — nine live wrappers, all heartbeating, all completing turns.
What was broken was the safety net.

**I diagnosed it wrong three times.**

1. *"Generated `supervisor.ps1` is version-skewed against the validator."* I compared `start_filetime`
   occurrences in the generated `.ps1` (0) against `supervisor.py` (39) — a meaningless comparison,
   since the 39 is mostly Python-side validation logic and the template only ever needed 2. I compared
   a script to a module. Disproved by generating the script from source into a scratch root and diffing:
   identical on every process-row field. The `agenttalk` on PATH was 0.80.0, same as source. I had filed
   a release blocker on this.
2. *"The wrappers' parent PID is dead, so ownership can't be proven."* All nine did share a dead parent
   — but `_owned_process_tree` never inspects the wrapper's own `parent_pid` for admission. dev-6 built
   that literal scenario and it produces a perfectly *complete* tree.
3. *"Nothing persists the owned tree."* I grepped state for `owned_process_tree`, found no file, and read
   absence-of-artifact as absence-of-code. `_plan_one` already persists a complete tree every poll. The
   fleet simply never reached *complete* again after being poisoned.

**What actually happened**, once dev-6's reproduction and my null measurement were combined: one
unrelated malformed row in a single whole-host snapshot fails `_snapshot_pid_integrity_error` for the
*entire poll*, and that one result feeds every agent planned that cycle — which is the only arithmetic
that yields nine agents, one reason code, one poll. Then the stickiness: an INVALID prior returns
UNCHANGED regardless of what any later snapshot proves. So a transient bad row at 20:31:19Z poisoned all
nine at once, every subsequent poll was clean, and it made no difference.

That also explains why my own sample found *zero* bad rows hours later, and dev-6 had to use a synthetic
one — the poisoning moment was long past.

**The transient cause is nearly irrelevant. The stickiness is the whole defect.**

### The canary that disproved my own remedy

I told the operator the fix was to relaunch the wrappers, and tested it on one idle agent with nothing
assigned. **The supervisor never relaunched it** — 15 minutes, six poll decisions, wrapper definitively
absent throughout, no launch decision ever reached.

The HOLD pre-empts the LAUNCH path. So the state is *self-sealing*: the fleet cannot heal, and the
intuitive operator remedy converts an unrecoverable-but-**working** agent into a dead one. The warning's
own justification — "a partial kill could strand descendants" — does not even apply when nothing is
alive to strand.

Filed as **#150**. The single highest-value fix is: **a confirmed-absent agent must be launchable
regardless of the tree hold.** dev-8 is still down; I stopped after one canary rather than orphaning
eight more.

## The lesson that recurred all shift: the universal claim is the defect

Three separate instances, in three different artifacts:

- 87-A's early Q4 rounds — the enumeration was careful; the word **"every"** was false.
- PR 108 — `rejected_count` was the right closure; the claim that `omitted_count == 0` meant
  "completely described" was false. It counts admitted identities excluded by the cap, **not rejected
  discovery branches**.
- 87-A revision 15 — the disambiguation is real where applied; the statement that it was applied
  **throughout** is false, with four surviving counterexamples.

In every case the machinery was sound and the sentence asserting its scope was not — and the sentence is
what a reader relies on. **A global claim is a testable assertion and should be checked like one, or not
made.**

Its sibling: **hand enumeration is the wrong instrument for a universal property.** dev-6 enumerated
sixteen exclusion sites by hand, classified each with reasons, and the connector still found paths that
lose a candidate — two of which were not `invalid_reason` sites at all. The answer was not a fourth site
but `discovered == admitted + rejected`, checked once after the walk.

## Two independent lenses disagreed on a fact, and that was worth the cost

On 87-A revision 14 reviewer-3 said HOLDS and reviewer-1 said BREAKS on the same field. I adjudicated
against the document rather than picking a reviewer: `issuer_supervisor_start_guard` resolves through
`ExecutionGateCaptureV1.guarded_start` to a generic token, while the exact-FILETIME type is used only for
*targets*. reviewer-1 was right.

reviewer-3's error is worth keeping because it is subtle and reusable: it verified the exact types on
`source_targets`, and let that carry to the issuer guard without tracing it down. **A strong property
nearby does not transfer to the field you actually depend on.**

The document's own vocabulary caused it — "exact" meaning an exact-identity *type* in two lines and
"exactly this other record's value" two lines later.

Round 8 split the same way for a different reason: reviewer-3 tested the vocabulary section's *declared*
scope; reviewer-1 tested the *claim's* scope. **When a document states a global property, the scope to
test is the property's scope, not the section announcing it** — otherwise the check can only confirm what
the author already believed.

## My premises kept propagating into other people's work

- I told both reviewers to model 87-A's attended escape on `--reset-process-tree-ownership`, calling it
  "exact-identity-verified". It is not, for invalid/truncated records. The exemplar I handed them carried
  the same weakness as the blocker.
- I instructed dev-6 to **name the remedy** in the HOLD message. It named
  `--reset-process-tree-ownership`, which the reset implementation *refuses* for entryless placeholders —
  precisely the sticky holds the message targets. We nearly shipped a message telling operators to run a
  command that cannot work. Worse than naming none.
- I ordered two changes in one 87-A brief that do not compose: make custody unmintable from replayable
  provenance, *and* defend the kill half as retry-safe. Retry-safe needs a retry path; unmintable forbids
  one. dev-4 executed both faithfully and the contradiction was mine.
- I proposed disproving issuer liveness via the existing instance-claim token. dev-4 refuted it with
  evidence: the token is documented anti-accident, hard death leaves a valid marker forever, and
  decisively — **possession of the token is not the effect authority**, so a marker swap revokes nothing.
  And replacing the marker itself calls the tolerant comparison revision 15 exists to refuse, so a
  successor claim *consumes* the disputed decision rather than proving it.

Every one of these was caught by someone else. The pattern is that a lead's premise travels further and
faster than a lead's instruction, and gets checked less.

  third error message contained the answer. The forcing gate is good design; the failure is that the WARN
  reporting an obligation never names the command that discharges it. Same defect as #150's "operator
  attention required" with no remedy.

I also found I had been running off my **inbox** and not my **owed-ledger** — different queues, only one
of them unmissable.

## Tooling traps that produced confident wrong answers

Twice my own shell silently produced a wrong result that looked real: backticks inside a double-quoted
bash string ran as command substitution and deleted a tool name from a posted PR comment; and Git Bash
mangled `revision:path` into a Windows path, returning **empty** output that read as "the bump did not
land". Both were caught only by reading back what actually happened. Compose review prose in files, and
treat an empty result as a fact about the query first.
